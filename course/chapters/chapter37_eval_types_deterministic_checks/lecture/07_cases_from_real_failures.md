# 7 · Building the case set from real failures, not from imagination

*Lecture 37, part 7 of 8 · ~20 min reading*

## 7.1 You cannot write the criteria before you have seen the failures

The natural way to start an eval set is to sit down and think of test cases. It does not work, and the reason is not laziness. Shankar, Zamfirescu-Pereira, Hartmann, Parameswaran and Arawjo, studying people who were trying to write evaluation criteria for LLM outputs, found "a phenomenon we dub *criteria drift*: users need criteria to grade outputs, but grading outputs helps users define criteria." Stronger: "some criteria appears dependent on the specific LLM outputs observed (rather than independent criteria that can be defined a priori), raising serious questions for approaches that assume the independence of evaluation from observation of model outputs." The criteria for *your* system's failures do not exist until you have watched your system fail. An imagined case set encodes the failures you could think of, which are by construction not the ones that surprised you.

Google's "Rules of Machine Learning" has carried the same warning since before LLMs. Rule #23: "You are not a typical end user." "While there are a lot of benefits to fishfooding and dogfooding, employees should look at whether the performance is correct" — your own usage is not the distribution. Rule #27: "Try to quantify observed undesirable behavior" — "measure first, optimize second." The move from a complaint ("it gets dates wrong") to a criterion ("relative-date phrases resolve to the correct absolute date") to a case set is the whole discipline, and it starts from an *observed* complaint.

## 7.2 Error analysis: the highest-leverage hour you will spend

Hamel Husain calls error analysis "the single most valuable activity in AI development and consistently the highest-ROI activity," and the FAQ he maintains with Shreya Shankar names it the most important step. The procedure is borrowed from qualitative research and has two named phases.

**Open coding.** "Review and write open-ended notes about traces, noting any issues." No taxonomy yet; you do not know the categories. A spreadsheet, one row per trace, one free-text column for what went wrong. Hamel's field guide describes the Nurture Boss case: "We started with a spreadsheet where each row represented a conversation. We wrote open-ended notes on any undesired behavior."

**Axial coding.** "Categorize the open-ended notes into a failure taxonomy." Cluster the notes into failure modes; an LLM can help cluster ("Then we used an LLM to build a taxonomy"), but a human decides. In that case, "after annotating dozens of conversations, clear patterns emerged": "just three issues accounted for over 60 % of all problems" — conversation flow, hand-off failures, rescheduling. One of them, relative-date handling, failed 66 % of the time on phrases like "next Tuesday"; once named and fixed, "their date handling success rate improved from 33 % to 95 %."

That distribution — a few failure modes dominating — is the normal shape and the reason the first thirty traces are worth more than the next three hundred. The stopping rule is saturation: "continue until new traces stop revealing failure modes or changing existing ones." The FAQ's numbers: at least 30 traces reviewed yourself; a working pool of ~100; between review cycles, "10–20" production traces a week with attention to outliers; every 2–4 weeks, 100+ fresh traces.

Eugene Yan describes the same loop as "simply the scientific method in disguise": "By looking at the data, we learn where the system works well, and perhaps more crucially, where it fails. … By looking at data such as retrieved documents, reasoning traces, and erroneous outputs, we can prioritize failures to fix." He also names the cost of skipping the human step even when a judge exists: "human annotators can miss as many as 50 % of the defects due to fatigue after looking at hundreds of samples" — which is an argument for small, frequent sessions, not for none.

## 7.3 From a failure to a case

A failure mode becomes a case in three moves, and the third is where most teams stop short.

**Capture the trace.** Braintrust's regression-test guide lists what a production trace contains that a made-up case cannot: "the real inputs, outputs, tool calls, retrieved context, prompt versions, model versions, and runtime metadata." Lecture 35's per-iteration log and Lecture 42's spans are how you have it. Without the retrieved context you cannot reproduce a RAG failure; without the tool results you cannot reproduce an agent failure; without the model version you cannot know whether it still fails.

**Write the check.** For each failure mode, decide whether "an objective rule can identify the failure" — then it is a deterministic check (part 5) — or whether "the failure requires subjective or domain-specific judgment" — then it is a judge (Lecture 38), and you will need "100 to 200 examples for each failure mode" to calibrate it. The date-handling failure is deterministic: the resolved date either equals the correct one or it does not. A "tone too formal" failure is not.

**Generalize, then keep one.** A single failing trace is a regression test for that trace. A *failure mode* is a family; the case set should hold representatives of the family, not every instance. Braintrust: "Group traces by failure mode, keep one representative case per cluster, and store the related span IDs in metadata," because "a regression dataset can become too narrow when every production failure is added as a separate permanent test case." Anthropic's guide agrees on the starting scale — "20–50 simple tasks drawn from real failures is a great start" — and on the seed: "Begin with the manual checks you run during development — the behaviors you verify before each release and common tasks end users try."

## 7.4 Every bug becomes a case before the fix merges

Software engineering settled this decades ago, and the clearest primary statement is SQLite's testing page: "Whenever a bug is reported against SQLite, that bug is not considered fixed until new test cases that would exhibit the bug have been added to either the TCL or TH3 test suites. … Over the years, this has resulted in thousands and thousands of new tests. These regression tests ensure that bugs that have been fixed in the past are not reintroduced." The project has 590 times as much test code as library code (92,053 KSLOC against 155.8 KSLOC) and 100 % branch coverage — and the regression rule is the part that compounds.

For an LLM system the rule is the same and the mechanics are slightly different, because the "bug" may be a prompt change, a retrieval change, or a model swap rather than a code change, and because the fix may be a rate improvement rather than a binary. The production drill this week is the rule applied retroactively: take the last three things you fixed in your agent, and for each one produce the case that would have caught it — the trace, the check, the expected outcome — and confirm the case fails on the pre-fix commit and passes on the post-fix one. From this week on, the sequence is: failure observed → trace captured → case written → case fails → fix → case passes → merge. Hamel's Rechat "has hundreds of these unit tests. We continuously update them based on new failures we observe in the data."

Braintrust names the reason this is not optional for LLM systems specifically: "A hallucinated citation, a missed retrieval, an invalid tool argument, or a format violation may not trigger an exception." Nothing crashes. Without a case, the bug is fixed by a prompt edit that nobody can later prove still works.

## 7.5 Closing the loop from production

Part 2 said offline and online use different data. This is where they meet. Online monitoring (Lecture 40, Lecture 42) surfaces a trace that a reference-free check or a user flagged; error analysis names its failure mode; a case is minted with a reference or a check; the case joins the working set — and, on the schedule from part 4, a fraction of new cases go to the held-out slice before anyone tunes on them. Anthropic's guide describes the hand-off: "Production monitoring kicks in post-launch to detect distribution drift and unanticipated real-world failures." Braintrust: "Refresh the regression dataset as part of incident triage and failure review, since it should grow as new production failure patterns emerge." LangChain's heading for the same idea is the slogan: "Turn production failures into regression coverage."

Two guards keep the loop honest. First, the *balance* from part 3: a set that is all failures teaches you nothing about what the system does well and will make every score look like a catastrophe; keep passes in it, and keep the paired near-neighbours (part 5 §5.4) so that fixing a refusal bug does not silently introduce over-refusal. Second, the *representativeness* warning: a set built only from complaints over-represents the users who complain. Sample some traces uniformly, not only the flagged ones, or your set will teach the system to please the loud.

## 7.6 What to carry forward

You cannot write good criteria before observing failures, because criteria come *from* grading outputs. Read at least thirty real traces with open-ended notes, cluster the notes into a failure taxonomy, and expect a few modes to dominate. For each mode: capture the full trace, decide deterministic-check versus judge, and keep one representative case per cluster rather than every instance. From now on a bug is not fixed until a case exists that fails before the fix and passes after; start with the last three. Feed production failures back into the working set and route a fixed share of new cases to the held-out slice, keeping passes and paired near-neighbours in the set so it measures the system rather than the complaints.
