# 8 · Where pytest ends and evaluation begins — and why both gate CI

*Lecture 37, part 8 of 8 · ~25 min reading*

## 8.1 A test asserts a property; an eval estimates a rate

The whole distinction fits in one sentence, and everything in this part is a consequence of it.

A **test** asserts that a property holds. It runs once per case, its result is a boolean, and the correct pass rate is 100 %: a failing test is a bug in the code or a bug in the test, and either way somebody fixes something before merging. Everything in part 5 that does *not* call a model is a test in this sense — the schema validator, the citation parser, the trajectory predicates, the case loader. If your `check_tool_order` function is wrong, that is a pytest failure like any other.

An **eval** estimates a rate. It runs the *model-bearing* system on a case, possibly several times, applies checks — deterministic or judged — and the meaningful result is the fraction of cases (or trials) that pass, with an interval. Hamel Husain says the unfamiliar part out loud: "Unlike traditional unit tests, you don't necessarily need a 100 % pass rate. Your pass rate is a product decision." The Hamel–Shankar FAQ goes further: be "wary of optimizing for high eval pass rates," because "a 70 % pass rate might indicate a more meaningful evaluation" than a suite that always passes. A suite at 100 % has stopped measuring anything except that you built it to pass.

The two are made of the same materials — same assertions, same runner, often the same `pytest` invocation — and they differ in what a failure *means*. A test failure means "fix before merge." An eval failure means "the rate moved; is the move real, and is it acceptable?" Conflating them produces two failure modes: treating evals as tests (the build goes red on noise and everyone learns to ignore red) or treating tests as evals ("the schema check only fails 3 % of the time, ship it").

## 8.2 Why the boundary is not where the tooling puts it

Every eval framework runs under pytest, which blurs the line on purpose. DeepEval "plugs into pytest via `assert_test()` and the `deepeval test run` command, so every push runs the same evals," with `@pytest.mark.parametrize("golden", dataset.goldens)` over the case set. LangSmith's `@pytest.mark.langsmith` decorator syncs each test to a dataset example and "by default LangSmith collects the pass/fail rate under the `pass` feedback key" — note *rate*. promptfoo emits "exit code 1" when a threshold is breached, and its documented quality-gate idiom is a pass-rate floor: `if (( $(echo "$PASS_RATE < 95" | bc -l) )); then exit 1`. OpenAI's Evals API returns `"result_counts": {"total": 3, "errored": 0, "failed": 0, "passed": 3}` — a count vector, not a boolean; the reduction to a merge decision is code *you* write, and that code is where the policy lives.

The tell is that DeepEval's CI page has a section titled **"Handling Flaky Test Cases."** A framework that needs that heading is telling you its assertions are not tests. This is not a criticism — it is the honest shape of the thing — but it means the pytest wrapper is a *transport*, and the semantics have to come from you.

Google's experience with ordinary software is the calibration point. Their deterministic suites are not deterministic: "almost 16 % of our tests have some level of flakiness," "about 84 % of the transitions we observe from pass to fail involve a flaky test," and the remedy was statistical — a flaky-marked test "report[s] a failure only if it fails 3 times in a row," and persistent offenders are quarantined off the critical path. Luo, Hariri, Eloussi and Marinov's study of 201 flaky-test fixes across Apache projects found the causes were mundane (async wait 45 %, concurrency 20 %, test-order dependency 12 %) and that "78 %" of flaky tests were flaky from the first time they were written. Ordinary software acquires non-determinism by accident and fights it. An LLM system has it by construction, so the machinery — repetition, thresholds, quarantine, a noise floor — goes in on day one.

## 8.3 Both gate CI, in different stages

Martin Fowler's deployment pipeline is the frame: "A deployment pipeline is a way to deal with this by breaking up your build into stages. Each stage provides increasing confidence, usually at the cost of extra time. Early stages can find most problems yielding faster feedback, while later stages provide slower and more thorough probing." The line between test and eval is a line between stages, drawn by cost and latency rather than by importance.

**Commit stage — tests, and the deterministic evals that are cheap enough.** `pytest` over the harness code: the checks themselves, the case loader, the schema of the case files, the fixtures. This must be 100 % green and takes seconds. Add to the same stage the deterministic checks over *recorded* trajectories (part 6 §6.7): they call no model, so they are tests of "does the check code still classify these known trajectories correctly," and they are free. The Hamel–Shankar FAQ's CI guidance: favour "assertions or other deterministic checks over LLM-as-judge evaluators" in CI, and cover "core features, regression tests for past bugs, and known edge cases."

**Merge gate — the deterministic eval suite against the live system.** Run the forty cases (Lecture 38 makes it the full harness) against the actual agent with the model pinned, `k` trials each where non-determinism warrants it, deterministic checks only. Report a pass rate with an interval and a per-case diff against the baseline. Block on a *regression* beyond the noise floor; warn otherwise. This costs minutes and cents and runs on every PR that touches a prompt, a tool schema, a retrieval config or a model version.

**Post-merge / nightly — the expensive evals.** Judge-based metrics, the held-out slice on its schedule, the capability set, repeated trials for `pass^k`. These produce trend lines and the drift dashboard, not merge decisions (Lecture 38's gate; Lecture 42's dashboards).

Caching makes the middle stage bearable. LangSmith records LLM calls to `tests/cassettes` and replays them ("All requests will be cached … and loaded from there on subsequent runs"); promptfoo caches with a 24-hour TTL keyed on prompt and config hashes; Braintrust's GitHub Action defaults `use_proxy: true` for exactly this. A cached run tests your *code* against *yesterday's model outputs* — which is a test, not an eval, and is the right thing to run on a PR that did not touch the prompt.

## 8.4 The gate itself: threshold, noise, blocking, rollback

The system-design drill this week is this section done properly, on a whiteboard, with numbers and a rollback for each surface. What follows are the principles; the drill asks you for the mechanism.

**Compare per case, not by aggregate.** Miller's recommendation for comparing two systems: "conducting statistical inference on the question-level paired differences," because case scores are correlated across systems and pairing "represent[s] a 'free' reduction in estimator variance." The gate's input is not "was 82 %, now 79 %"; it is "cases 7, 19 and 33 flipped from pass to fail, case 12 flipped from fail to pass." Braintrust's PR comment shows the artefact: per-scorer average, delta in percentage points, and counts of per-case improvements and regressions (`8 🟢 | 4 🔴`).

**Measure the noise floor before you set a threshold.** Run the *unchanged* system against the suite several times. The spread you see is what a "difference" has to exceed to mean anything; Google's flakiness definition — "a test that exhibits both a passing and a failing result with the same code" — is the operational definition of a case that contributes to it. Blum & Hardt's Ladder is the policy: only act on a change that beats the incumbent by more than the step size. Anthropic's regression target ("nearly 100 %") and capability target ("start at a low pass rate") say which suite the threshold applies to.

**Decide what blocks and what warns.** Braintrust's Action defaults `terminate_on_failure: false` — inform, not block — and that is the right *default* for a suite whose power you have not measured (part 4 §4.5: at forty cases you can see collapses, not five-point drifts). Block on: any deterministic check that must be perfect (Braintrust: "A schema-validity scorer may need a perfect score"; the forbidden-tool check from part 6 is another), a regression on a *pinned* set of regression cases, and any flip on a case tagged as a fixed production bug. Warn on aggregate movement within the noise floor. Never let a missing score count as a pass — Kayenta's canary judge returns an explicit `NODATA` classification when a metric is absent, and so should your gate.

**Rollback is a version pointer, not a redeploy.** The things that change an LLM system's behaviour — prompt, model ID, tool schemas, retrieval index version, decoding parameters — must each be versioned and pinned in the eval config, alongside the harness version and the case-set sha (seven pins in all), so that a baseline is comparable to anything at all. Anthropic's guarantee is the reason pinning works: "Anthropic does not update the weights or configuration of an existing model ID. When an updated version is available, it ships under a new model ID" — and note the scheme change, where 4.6-generation dateless IDs "map to a single, fixed model snapshot" while older dateless names were aliases. Rollback is then: point the prompt/model/index version back to the last configuration that passed the gate. Google's SRE Workbook chapter on canarying supplies the production half: a canary is "a partial and time-limited deployment of a change in a service and its evaluation"; "if we instead use a canary population of 5 %, we serve 20 % errors for 5 % of traffic, resulting in a 1 % overall error rate"; pick "the top few metrics … perhaps no more than a dozen"; and — the line that indicts comparing today's eval run to last week's number — "Before/After Evaluation Is Risky." Netflix's Kayenta turns that into an automated judge: a nonparametric test (Mann-Whitney U) per metric, a `Pass`/`High`/`Low` classification per metric, an aggregate score as "the ratio of metrics classified as 'Pass'," and an automatic abort: "If not, Spinnaker will abort the canary process." Your eval gate is Kayenta for prompts.

## 8.5 A worked shape

A PR changes the system prompt. The commit stage runs pytest over the harness in eight seconds: check code, case schema, fixtures, recorded-trajectory classification — green, or the author fixes it. The merge gate spins up the agent with `model = <pinned id>`, `prompt = <PR sha>`, `index = v14`, runs the forty working-set cases three times each with deterministic checks, and posts: pass rate 87 % ± 10, baseline 89 % ± 10 (clustered by case, so `n` is forty, not a hundred and twenty), per-case: two regressions (cases 07 and 31, both `tool_order` failures — `process_refund` before `verify_identity`), one improvement, thirty-seven unchanged. Case 07 is tagged `regression:incident-2026-08-14`. **Blocked**, and the reason is a fact — a specific check on a specific case that used to pass — not a judgement that the aggregate "looks worse." The author fixes the prompt, the gate goes green, the merge happens, the nightly run adds the judge scores and the held-out slice to the trend line, and next week's error analysis mints two new cases from production.

Nothing in that story required a model to grade anything. That is why the deterministic half comes first, and why the syllabus gave it a full lecture before the judge.

## 8.6 What to carry forward

A test asserts a property and must pass at 100 %; an eval estimates a rate and its acceptable value is a product decision. The pytest wrapper is a transport; the semantics — what a failure means — come from which stage it runs in: commit stage for tests and model-free deterministic checks over recorded trajectories, merge gate for the deterministic eval suite against the pinned live system, nightly for judges, the held-out slice and repeated trials. The gate compares per case, measures its noise floor before choosing a threshold, blocks on must-be-perfect checks and tagged regression cases, warns on aggregate drift, treats a missing score as `NODATA` rather than a pass, and rolls back by re-pinning prompt, model, tool schemas, index and parameters to the last passing configuration. Both kinds gate CI because they fail differently: the test catches the bug in your code, the eval catches the bug in your system's behaviour, and a system with a model in it has both.
