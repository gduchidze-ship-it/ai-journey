# 3 · Golden datasets versus synthetic datasets

*Lecture 37, part 3 of 8 · ~20 min reading*

## 3.1 Two kinds of case, two kinds of trust

A **golden** case is an input paired with an expected outcome that a human has looked at and vouched for. The input came from somewhere real — a production log, a support ticket, a bug report, a domain expert's example — and the expected outcome is either a reference answer or a set of properties the answer must have, written by someone who knows what correct means here. Its value is that you trust it. Its cost is that a person had to make it.

A **synthetic** case is an input (and sometimes an expected outcome) generated by a program — usually an LLM prompted with your documents, your tool schemas, or a grid of scenario dimensions. Its value is volume and coverage: you can make five hundred in an afternoon and deliberately sweep corners real traffic has not reached yet. Its cost is that you do not trust it until you have checked it, and checking it is the same work that would have made it golden.

The field has converged on an ordering. DeepEval's synthesizer docs, which exist to sell synthetic generation, state it against their own interest: "Synthetic data generation helps you bootstrap evaluation datasets when you do not yet have enough representative examples, but it should complement — not replace — real data," and "It is easy to abuse synthetic data because it is so readily available. It is important to use it sparingly." Their recommended priority is (1) human-reviewed curated datasets, (2) production traffic samples, (3) synthetic generation. LangSmith's concepts page lists the same three sources — "manually curated examples," "historical traces," "synthetic data" — and recommends starting with "10–20 high-quality examples covering common scenarios and edge cases." OpenAI's best-practices guide: "Use a mix of production data … and datasets created by domain experts."

## 3.2 Building the golden set

The recipe, from Hamel Husain's and Shreya Shankar's FAQ and Hamel's judge guide, has numbers attached.

*Start by reading.* "Review at least 30 traces yourself," and keep going "until new traces stop revealing failure modes or changing existing ones. Qualitative researchers call this theoretical saturation." Hamel's own heuristic: "I start with around 30 examples and keep going until I do not see any new failure modes." A working pool of "roughly 100 diverse traces" is the guardrail.

*Then label.* Binary, not Likert: "Binary decisions are also faster to make during error analysis — you don't waste time debating whether something is a 3 or 4." Eugene Yan's target for the labelled set is balance — "Ideally, we should have a 50:50 split of passes and fails that spans the distribution of inputs" — and "at least 50–100 failures out of 200+ total samples." Failures are the scarce resource; a set that is 95 % passes teaches you nothing about how the system fails.

*Then size.* "Aim for about 100 examples per failure mode, with enough Pass and Fail examples to measure both classes. Below 60 examples, the confidence intervals are often too wide." That 60 is the floor for a *judge* (Lecture 38); for a deterministic regression suite the arithmetic in part 4 says how many cases you need to detect a given drop. Anthropic's agent guide gives the minimum viable start: "20–50 simple tasks drawn from real failures is a great start."

*Then split.* Never let the same cases serve as both tuning material and report card. The split Hamel and OpenAI's cookbook both prescribe is roughly 10–20 % train (examples that may appear in a prompt), 40–45 % dev, 40–45 % test — part 4 explains why the last slice is looked at "one time."

The build this week asks for forty cases. Forty is not a statistical sample of anything; it is the seed of a set that Rechat, in Hamel's case study, grew to "hundreds," and the Hamel–Shankar FAQ says "a purpose-built eval set often grows to 100 or more examples." Forty is enough to build the *structure* — the schema, the check types, the held-out slice, the CI wiring — so that case forty-one costs five minutes.

## 3.3 Generating synthetic cases

Synthesis is a coverage tool. The mechanics that work share one shape: define the *dimensions* of variation first, generate combinations, then generate an input per combination.

RAGAS's test-set generator makes the grid explicit. Its scenario is "a combination of: Nodes, Query Length, Query Style, and Persona," where the nodes come from a knowledge graph built over your documents, and query types span single-hop versus multi-hop ("a multi-hop query involves multiple steps of reasoning, requiring information from two or more sources") and specific versus abstract. Its own list of what an ideal test set needs includes "covers wide variety of scenarios as observed in real world" and "continually updated to prevent data drift."

The Hamel–Shankar FAQ gives the hand-built version: "Define important dimensions first" (for a real-estate assistant: user persona, property type, request type, tone), then "Write 20 tuples by hand," then prompt an LLM to expand each tuple into a realistic query, then — the step people skip — "run these synthetic queries through your actual system to capture full traces." A synthetic *input* is cheap; a synthetic *expected output* is where the trust problem lives, so the FAQ's workflow generates inputs, runs the real system, and has a human grade the resulting traces. DeepEval's Synthesizer defaults are worth knowing because they show the shape of the machinery: `max_goldens_per_context = 2`, `max_contexts_per_document = 3`, so at most six generated cases per source document, with quality thresholds on generated contexts. Anthropic's console can "auto-generate test cases" and run them against two prompts side by side; that is the same idea with the labelling left to you.

For an *agent*, the dimensions are different and more mechanical: which tool the task requires, how many tools in sequence, whether a tool will fail, whether the user's request is under-specified, whether the request should be refused, whether the answer exists at all. Sweep those and you get cases that real traffic will take months to produce — which is exactly what they are for.

## 3.4 What synthetic cases get wrong

Every serious source lists the same risks, and they are all distribution risks.

*They are too easy and too clean.* Eugene Yan on synthetic defects: "I find these synthetic defects problematic. They tend to be out-of-distribution … [they] may fail to detect the messy, organic issues that actually affect our users." His workaround is to use "smaller, less capable models to generate outputs" so the failures are "organic" rather than injected. OpenAI's best-practices guide lists "Biased design: Creating eval datasets that don't faithfully reproduce production traffic patterns" as an anti-pattern.

*They miss what the generator does not know.* The FAQ's five scenarios where synthetic data is unreliable: "complex domain-specific content" ("LLMs often miss the structure, nuance, or quirks of specialized documents"), "low-resource languages or dialects" ("LLM-generated samples are often unrealistic"), when validation is impossible, high-stakes domains, and underrepresented user groups. The generator is a model with the same blind spots as the model under test — Shankar et al.: "LLM-generated evaluators simply inherit all the problems of the LLMs they evaluate."

*They can be reproduced from the same prior.* If the generator and the system under test share a model family, the cases are drawn from the distribution the system finds most natural. A high pass rate on those says the system agrees with itself.

The rule that falls out: a synthetic case is a *candidate*. It becomes golden when a human has read the input, decided it is realistic, and vouched for the expected outcome. Until then it belongs in the capability set (part 2 §2.5), where a low pass rate is information rather than a failed gate.

## 3.5 Anthropic's dissent, and why it is not one

Anthropic's evaluation guide says "Prioritize volume over quality: More questions with slightly lower signal automated grading is better than fewer questions with high-quality human hand-graded evals." Read against Hamel's "read thirty traces yourself" this looks like a contradiction. It is not; it is a different object. Anthropic is describing *capability* evals with automated grading at model scale — 1,000 tweets, 500 patient queries — where the grader is cheap and the question is "how good is the model." Hamel and Yan are describing *product* evals where each label is a domain expert's hour and the question is "how does *my* system fail." Volume wins when grading is free; curation wins when grading is the bottleneck. Both are right about their own regime, and the deterministic checks in part 5 are precisely what make grading free enough for volume to win.

## 3.6 What to carry forward

Golden cases are real inputs with human-vouched expectations; synthetic cases are generated inputs whose expectations you have not yet vouched for. Curated first, production traces second, synthetic third — and synthetic to complement, never replace. Build the golden set by reading at least thirty traces to saturation, labelling binary, aiming for balance between passes and fails, and splitting before you tune. Generate synthetic cases from an explicit dimension grid and run them through the real system; treat them as candidates until a human promotes them. Forty cases is a structure, not a sample.
